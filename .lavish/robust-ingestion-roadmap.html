RAG Quality Studio · ingestion review

Make extraction a real, inspectable data product.

The highest-value change is not “add more cleaning switches.” It is to introduce a canonical structured document between source fetching and chunking, then make extraction quality, transformations, and provenance visible and reproducible.

Recommendation: first build one shared ExtractedDocument → CleanedDocument → Chunk path for every connector. Then add layout-aware PDF extraction with page-level OCR fallback, deterministic block-aware cleaning, quality gates, and semantic/token chunking. Do not begin with an LLM cleaner: it adds cost and nondeterminism before the basic structure is trustworthy.

Target architecture

One intermediate representation, many extractor adapters

Canonical block contract

Block { id, type: heading | paragraph | list_item | table | code | image_caption, text, page, bbox?, heading_path[], language?, source_span, extractor_confidence?, warnings[] }

Important storage boundary

Keep the immutable raw artifact. Store or reproducibly regenerate extracted and cleaned representations with their versioned configs and hashes. A chunk should point back to block IDs and source spans—not only character offsets in a flattened string.

Beyond cleaning

Extraction quality is wasted if chunking destroys structure

Section-aware token chunks

Split at heading and block boundaries, then by tokenizer only when a section is too large. Keep character windows as a legacy profile.

Parent/child retrieval

Embed compact child passages, but return the larger parent section as evidence. This improves matching without starving generation context.

Separate embedding text

Prepend document title and heading path to embedding_text, while keeping evidence_text faithful to the source and citations.

Product experience

Make every transformation inspectable

Preview should show four synchronized panes

  1. Raw: PDF page/HTML/block source metadata, safely rendered.
  2. Extracted: detected blocks, reading order, tables and OCR markers.
  3. Cleaned: before/after diff with each removed or rewritten span attributed to a rule.
  4. Chunks: boundaries, token counts, heading context and eventual embedding text.

Per-item stage report

Record extractor used, native/OCR pages, warnings, removed characters/blocks, quality score, dedupe decision, chunk count, duration and estimated/actual OCR cost. Current run-level node status is not enough.

Recommended delivery order

Four vertical slices, each usable on its own

0

Make the current nodes truthful

Create shared extractor/cleaner interfaces, execute Clean for uploaded files, remove connector-specific cleaner copies, and add editable settings plus before/after preview. Keep v1 pipeline versions executable with explicit legacy semantics.

1

Introduce the structured document IR

Persist blocks and source spans, implement layout-aware PDF extraction and automatic page-level OCR fallback, preserve HTML/Notion/Confluence hierarchy, and add quality gates. Reprocessing must produce a new immutable revision.

2

Structure-aware cleaning and chunking

Add detected headers/footers, dehyphenation, table handling, token/section chunks, heading enrichment, and exact + near-duplicate reports. Build index variants from one source snapshot to compare chunk profiles without refetching.

3

Measure ingestion quality

Create a reviewed “golden extraction” set with PDFs, scans, columns, tables, Notion/Confluence nesting and noisy web pages. Track block-order accuracy, table cell accuracy, OCR character error rate, removed-boilerplate precision, chunk boundary quality and downstream retrieval recall.

Schema direction

Prefer profiles and bounded policies over arbitrary scripts

Extract node v2

strategy: auto | native | layout_aware ocr: mode: off | auto | always languages: [eng] rotate_pages: true tables: preserve | markdown | plain_text quality_policy_id: default-v1

Clean node v2

steps: - unicode_normalize: NFC - remove_repeated_headers: { page_ratio: 0.6 } - dehyphenate: conservative - reflow_lines: preserve_blocks dedup: { mode: exact_and_near, threshold: 0.92 }

Avoid arbitrary user regex, Python, selectors without validation, or LLM prompts as executable cleaning logic. Start with typed, bounded rules. If LLM enrichment is later added, snapshot provider/model/prompt, retain the original text, label generated content, and expose its cost and failures.

Build vs integrate

Own the contract; plug in extraction engines

Own in RAG Studio

IR schemas, provenance, quality policy, transformation audit, job fencing, immutable revisions, preview UI, chunk profiles and evaluation.

Evaluate as adapters

Docling for layout/table/OCR-aware conversion; OCRmyPDF/Tesseract for scanned PDF preprocessing; Apache Tika when broad format coverage becomes a requirement.

Do not couple to

A vendor-specific JSON shape. Normalize every engine into the application-owned ExtractedDocument contract and version the adapter.

First acceptance gate

A robust first release is done when…

  • A mixed text/scanned PDF succeeds with per-page native/OCR provenance; a bad OCR page is warned or excluded by policy.
  • A two-column PDF preserves reading order, and a table keeps header/value relationships.
  • Repeated headers/footers are removed by a recorded deterministic rule without deleting matching body text.
  • The same cleaning settings behave identically for uploads, S3, Website, Notion and Confluence.
  • The user can compare raw, extracted, cleaned and chunked output before paying for embeddings.
  • Every chunk links to exact source revision, block IDs, page/section, extractor/cleaner versions and config hashes.
  • Changing extraction or cleaning produces a new immutable revision/index; prior experiments remain reproducible.
