# User documentation website: implementation plan

**Plan date:** 2026-09-26. **Scope of this document:** plan the documentation website and its content. No site, guide, screenshot, fixture, application link, or deployment is created by this phase. Reinspect the repository when implementation begins; this inventory is a dated baseline, not a permanent feature guarantee.

## 1. Documentation goals and audiences

The site should get a reader from an empty local workspace to a reproducible question with inspectable evidence, then explain how to choose and operate more capable paths. Each page must describe an observable application outcome, its prerequisites, failure states, and the exact saved version or artifact involved. It should disclose model charges and operational limits where those affect a decision.

| Audience | Tasks the documentation must enable | Primary path |
| --- | --- | --- |
| New user | Install locally, create a project, upload a sample file, prepare and publish a collection, ask a question, inspect cited passages. | Start → first workflow → Knowledge Base → Playground |
| Power user | Configure source collection and processing, inspect previews and findings, reuse a source snapshot, tune retrieval, save answer versions, compare them fairly. | Sources and ingestion → answer pipelines → experiments |
| API user | Authenticate in the configured mode, discover the actual request/response contract, create and poll versioned work, paginate and handle errors safely. | API guide → endpoint reference → workflow recipes |
| Self-hosting operator | Configure backend secrets and workers, judge readiness, back up database/artifacts/key material, recover jobs, rotate keys and assess shared-access gates. | Installation → configuration → operations and security |

**Boundary:** user guides teach UI tasks and concepts; the API guide teaches integration and links to generated operation contracts; operator docs cover runtime and recovery. `docs/implementation-plan.md`, `docs/architecture.md`, `docs/*-plan.md`, QA records and corpus baselines remain internal engineering evidence. They are sources to verify and rewrite, not pages to publish verbatim. The README remains a concise developer entry point; the site becomes the user-facing canonical guide after it is implemented and reviewed.

## 2. Current documentation and product audit

### What exists and what it proves

- `README.md` gives a local Compose/Vite start, provider configuration, workflow fragments, command examples and current API links. It is long, organized by historical milestones, and contains statements superseded by later work. Reuse tested commands and warnings after checking them; rewrite the task instructions.
- `docs/development.md`, `docs/deployment.md` and `docs/operations.md` contain useful connector, encryption, scheduling, backup, recovery and test detail. Rewrite for the operator and API audiences, with prerequisites and supported scope. `docs/operations.sql` is an operator aid, not a public API.
- `docs/architecture.md`, `docs/implementation-plan.md`, ingestion/retrieval/snapshot plans, QA screenshots and release baselines provide implementation evidence. They mix history, proposed behavior and results. Keep them outside the published navigation; cite a source internally during review.
- There is no dedicated docs-site package or `sample-data/` directory. The backend serves FastAPI's `/docs` route in principle; the current OpenAPI generation fails (see blocker below). The app has no help links in its project navigation.
- The frontend routes are hash URLs: Projects, then project **Overview**, **Knowledge Base**, **Pipelines**, **Playground**, **Experiments**, and **Settings**. Knowledge Base shows **Documents** and **Collections**, with **Collections** and **Source history** inside the latter. Pipelines has explicit **Answer pipelines** and **Ingestion pipelines** tabs. Playground has **Retrieval test** and **Pipeline test**, plus settings, past questions, sources and answer details. These labels come from `frontend/src/app/pages.ts`, `KnowledgeBase.tsx`, `IndexesWorkspace.tsx`, `PipelinesPage.tsx` and `PlaygroundToolbar.tsx` and should govern screenshots and task copy.
- Backend route modules cover health/readiness, projects, uploads and processing, indexes/retrieval, source connections, ingestion previews/runs/snapshots, schedules, query runs, pipelines, datasets and experiments. The implementation has local loopback-owner mode and configurable OIDC/project roles, but shared deployment still has explicit operator gates. Test files cover PostgreSQL, providers through doubles, security, connectors and browser workflows; external account behavior remains separately conditional.

## 3. Proposed documentation website

**Framework:** Docusaurus 3 with TypeScript configuration and Markdown/MDX content, in a separate `docs/site/` package. It is a React documentation stack compatible with this repository's authoring skills, supports structured sidebars and optional version snapshots, and emits a static build suitable for several hosts. Keep the product Vite app and its port `http://127.0.0.1:5273` unchanged; the docs site's local preview is a separate process. Pin compatible package versions only when implementation starts. Docusaurus' [docs hierarchy](https://docusaurus.io/docs/docs-introduction), [versioning guidance](https://docusaurus.io/docs/versioning), [search options](https://docusaurus.io/docs/search) and [static deployment model](https://docusaurus.io/docs/deployment) support this choice. MDX is for small, accessible examples; most pages should remain plain Markdown to simplify maintenance. A custom React marketing site would consume effort needed for content and verification.

**Repository layout:** preserve existing `docs/*.md` internal files; add `docs/site/{docs,src,static,sidebars.ts,docusaurus.config.ts,package.json}` and store approved public fixtures under `docs/site/static/examples/`. Generated OpenAPI artifacts, if committed, go under `docs/site/generated/` with a reproducible generator command and a diff check. Do not publish the surrounding internal `docs/qa`, plans, SQL files or secrets by accident. The built output goes to `docs/site/build/` and is ignored by Git.

**Routes and navigation:** use a dedicated docs origin with stable paths such as `/docs/start/first-workflow`, `/docs/ingestion/previews-and-runs`, `/docs/answers/evidence`, `/docs/experiments/compare`, `/docs/api/overview`, `/docs/operate/backup-and-restore`. A top-level landing page offers four audience paths. Sidebar groups: Start, Concepts, Knowledge Base, Sources and ingestion, Answers, Experiments, API, Operate, Reference. Breadcrumbs, in-page table of contents, previous/next and related links should connect task pages. Keep internal engineering docs out of search and sitemap. Configure redirects for renamed public slugs.

**Search:** first release should have working site-local full-text search that works without an external account; choose a maintained plugin only after compatibility and bundle-size verification. Docusaurus supports community local-search implementations, while Algolia DocSearch is the official hosted integration; a later switch is possible if the site is publicly crawlable and qualifies. Index page titles, headings, glossary terms and aliases; exclude generated duplicate fragments, internal artifacts and draft/future notes. Test keyboard focus and mobile results.

**Versioning:** initially publish one `current` documentation set with a visible product commit/release identifier and per-page `verified_against` metadata. Do not freeze copies for each internal milestone. Create a Docusaurus version only when a supported released application version diverges in user-visible behavior; retain the current and the supported older version and place version-specific warnings next to affected steps. Docusaurus itself advises that version snapshots add maintenance cost when they are not needed ([versioning](https://docusaurus.io/docs/versioning)).

**Mobile:** collapsible, keyboard-operable sidebar; no horizontal overflow at 390px and at a 200% equivalent width; code blocks scroll within their containers; diagrams get text alternatives and a readable zoom/download option; screenshots show an actual responsive state rather than shrinking desktop UI to illegibility. Search and version choice remain reachable by keyboard and screen reader.

**Application links:** add a visible Help/Documentation entry in the app shell and contextual links from upload validation, ingestion preview/run, source history, pipeline validation, evidence inspector, experiment metric help, and Settings/operations states. Each link uses a stable public docs route and opens without carrying a project ID, source URL, document text, credential, or query in the docs URL. Use a non-secret configured docs base URL; check target and fallback during build. Link back from docs to generic app paths, with project-specific instructions rather than invented IDs. Do not add links to unfinished pages.

**Hosting options, no action in this phase:** static host on a docs subdomain (recommended for clear separation and independent releases), static path behind an existing reverse proxy, or a repository pages host. Docusaurus emits static files; each option needs a correct canonical `url`/`baseUrl`, TLS, preview environment, cache rules, redirects, crawl policy and a release owner. A same-origin `/docs/` path must avoid the backend's FastAPI `/docs` on that backend origin. A private docs site can use local search without a crawler. Deployment and domain selection are a later authorized step.

## 5. End-to-end tutorials and examples

Create `docs/site/static/examples/sample.txt` with only fictional facts, for example: “Harbor Desk is open Monday–Friday, 09:00–17:00 UTC. Returns are accepted for 30 days. Escalations go through the help portal.” Create `reviewed.csv` with three human-reviewed rows: hours, return window, and an unanswerable question about weekend delivery. Add a short README stating expected answers, intended missing answer and fixture hash. No real person, credential, vendor token or sensitive source text belongs in fixtures. A small reviewed public Website fixture is required for a fully self-contained remote-source tutorial; until an HTTPS host is authorized and verified, the Website steps must explicitly use a reader-owned public source and be labeled conditional. A loopback fixture is unsuitable because the Website connector correctly blocks non-public destinations.

**Cost rule for every tutorial:** document that a configured embedding/answer/evaluator endpoint may charge for indexing, queries and scoring, including an in-flight request after cancellation. Put an estimated operation count where practical; label dollar cost unknown unless a pricing basis is known. Use deterministic test doubles only in the isolated test stack, never call them the production provider or promise a free live run.

### T1. Upload, publish, ask, inspect citations

- **Data/prerequisites:** `sample.txt`, local services, ready embedding and answer provider, isolated project.
- **Exact UI actions:** Projects → create **Harbor docs** → Knowledge Base → **Add document** → **Upload document** → select its row and **Start processing** → **Collections** → **Publish prepared documents** → wait for **Ready** → select **Use version [number] in a pipeline** → save an answer version → Playground **Pipeline test** → ask “When is Harbor Desk open?” → open **Sources & details** and select the citation.
- **Expected:** one successful processing version, a ready collection/index with fixed membership, a saved answer run, text supported by the passage and a source label that opens the supplied evidence. The unanswerable “Does Harbor Desk deliver on weekends?” should produce the app's insufficient-evidence behavior, subject to model behavior; do not promise a particular wording.
- **Failures/retry:** missing provider disables indexing/answering; invalid upload shows 422 or UI validation; empty/scanned PDF needs OCR; failed processing/index remains non-ready. Refresh status/history before retrying an ambiguous response; new run/version is created. Retain old ready index. Delete only the isolated project data after verifying deletion rules; no `down -v`.

### T2. Build and run an ingestion pipeline

- **Data/prerequisites:** prepared `sample.txt`, configured embeddings, isolated project. Use **Existing Files** so the path works without remote credentials.
- **Exact UI actions:** Pipelines → **Ingestion pipelines** → **New ingestion pipeline** → choose Existing Files and the uploaded document → inspect Source, Extract, Clean, Chunk, Embed and Publish settings → **Preview processing** → inspect Raw/Extracted/Cleaned/Changes/Chunks and quality outcome → save a version → choose destination → **Run ingestion** → inspect per-item run and published collection link.
- **Expected:** preview does not publish; run cites the exact saved version; one ready index appears only after all required items and embeddings succeed, with source/document provenance.
- **Failures/retry:** missing file, invalid graph, expired preview, excluded/failed quality decision, provider failure or cancellation. Correct settings and save a new immutable version; rerun safely. A cancelled request in flight may incur provider cost but cannot publish a cancelled index.

### T3. Reuse a source snapshot for another index

- **Data/prerequisites:** a ready snapshot from a bounded public Website tutorial source or a scoped test S3/Notion/Confluence account, retained raw artifacts, two compatible saved remote ingestion versions. A public fixture host is a publication gate for a no-account Website example.
- **Exact UI actions:** run the first remote pipeline with **Collect source & publish index** → Knowledge Base → **Collections** → **Source history** → select the completed snapshot → inspect included/revised items and downstream index → choose a compatible saved ingestion version with different chunk settings, a new collection name and the snapshot reuse action → run → inspect both indexes and their common snapshot ID.
- **Expected:** the second run uses stored revisions without another network collection; the new immutable index may have a different passage count; original ready index remains available. Embedding work and cost may recur.
- **Failures/retry:** missing/expired raw artifact, incompatible source/version, unavailable key, failed second processing, or legacy run without provable snapshot lineage. Do not silently refetch or use current source state; restore the referenced artifact/key if authorized or collect a fresh snapshot, then make a new version. Refresh history before another run.

### T4. Compare two answer pipelines fairly

- **Data/prerequisites:** `reviewed.csv`, one ready index (or two derived from the same snapshot), two saved answer-pipeline versions A and B differing only in a stated retrieval/prompt setting, configured evaluator.
- **Exact UI actions:** Experiments → download/inspect example CSV → preview and import `reviewed.csv` → select same dataset version and two exact saved answer versions → select supported metrics → start experiment → wait for terminal state → inspect aggregate counts, **Per-question comparison**, citations and CSV export.
- **Expected:** per-question outputs for both candidates, same dataset/source lineage called out, failures and unavailable metrics explicit. `context_recall` is unavailable on rows without a reference answer; faithfulness means support in supplied context. Generation and evaluation costs are separate; unknown is not zero.
- **Failures/retry:** missing evaluator/embedding config, malformed CSV, failed item, cancellation, model variability or different source versions. Fix config/data, save/import a new version, run a new experiment; never edit the prior snapshot or discard failed rows to improve the mean.

### T5. Diagnose a failed or low-quality ingestion run

- **Data/prerequisites:** synthetic PDF with one scanned page or a reviewed text fixture containing repeated sections and a safe synthetic email, plus a schema-v2 ingestion draft.
- **Exact UI actions:** preview exact unsaved settings → inspect per-item status and extraction page origin → compare Extracted/Cleaned/Changes/Chunks → inspect quality/language/duplicate/sensitive finding counts and publication decision → adjust OCR language or quality/cleaning policy in node settings → preview again → save a new version → run and inspect published membership or explicit exclusion.
- **Expected:** actionable finding and item status; a strict failure or exclusion does not silently publish the bad item; redaction placeholders, not original synthetic values, appear in downstream evidence.
- **Failures/retry:** unavailable OCR language, timeout/page bound, protected content permission denial, expired preview/artifact or provider failure. Use capability endpoint, adjust bounded settings, retry as a new preview/version; avoid deleting history or weakening the threshold solely to force success.

## 6. Writing and visual standards

**Reusable page template:** title and one-sentence outcome → availability/verified-against badge → prerequisites (including cost and permission) → numbered steps with exact UI labels or complete commands → expected result with artifact/version ID to inspect → likely errors and safe retry/reset → next step and related pages. Reference pages may replace numbered steps with a contract table but still include one runnable request and expected response shape. Keep heading hierarchy consistent and put the task outcome above conceptual background.

- **Terminology:** match current UI capitalization: **Knowledge Base**, **Documents**, **Collections**, **Source history**, **Source snapshots**, **Answer pipelines**, **Ingestion pipelines**, **Playground**, **Experiments**. Explain that API `knowledge_set`/`index_version` map to UI collection/index; distinguish source snapshot from a ready index and preview from execution. Never call vector distance a confidence score.
- **Screenshots:** use an isolated seeded project, consistent desktop/mobile viewports, no credentials/real user data, visible control labels and useful alt text. Give each screenshot a purpose and capture metadata (application commit, viewport, date, scenario). Avoid a screenshot of a transient spinner as the sole proof of a feature. Re-capture when labels or layout change.
- **Diagrams:** source → extraction → cleaning → chunks → embeddings → index → retrieval → answer → evaluation, with snapshot and saved-version branches. Provide a text alternative and ensure color is not the only carrier of state.
- **Accessibility:** meaningful links, sequential headings, keyboard-reachable code copy/search/sidebar, readable contrast, no hover-only instructions, labeled images, tables with headers and mobile reflow. Instructions must work without dragging nodes; point to the selected-node forms.
- **Code/API samples:** complete commands with working directory and required setup; shell placeholders such as `<PROJECT_ID>` clearly marked; JSON matching validated schemas; show status codes, pagination and polling; never paste a credential or real document text into a URL. Prefer generated response examples from the repaired OpenAPI plus human-reviewed end-to-end recipes. For read-only calls, use loopback examples; for writes, use synthetic isolated data.
- **Callouts:** `Prerequisite` for settings, `Cost` for provider work, `Security` for raw/credential access, `Version note` for changed behavior, and `Limitation` for unsupported outcomes. Do not use a success-colored callout for an unverified live integration.
- **Capability claims:** display **Verified locally** only with a dated test/run reference; **Requires configuration** when provider or key absent; **Requires live account validation** for external connector/KMS behavior; **Planned** only in a clearly separated limitations/future note. Never turn roadmap statements into present-tense instructions. For version-specific steps, show the first/last applicable app release or commit and link to the older docs snapshot when one exists.

## 8. Verification and maintenance

**Automated checks:** docs build with broken-link/anchor failure; Markdown/MDX lint and formatting; spell/terminology check for product labels; fenced shell/JSON/Python snippet syntax checks; generated OpenAPI JSON validation and drift detection; static asset/alt-text audit; no secrets/real data check; search index smoke test. Test all internal cross-links and selected external official links. Assert that every public sidebar target exists and every app Help target maps to an implemented page. Run docs build from a clean install with pinned lockfile.

**Human/browser checks:** at least 1440px desktop, 720px/200% equivalent and 390px mobile; keyboard navigation, screen-reader landmarks and focus order, table/code overflow, search results, version label, diagram alternatives and screenshot legibility. Execute T1–T5 on an isolated PostgreSQL/pgvector stack with synthetic fixtures; use deterministic provider transport for repeatable journeys and a separately authorized, bounded live-provider/account acceptance only when the page claims it. Record commit/configuration, expected vs actual states, screenshots and any cost. Test refresh, failure, cancellation, missing credentials and safe retry. Do not reset developer data or remove named volumes.

**Maintenance contract:** a product change that alters a UI label, workflow, API schema, security boundary, provider, migration, metric or operational step must include a docs-impact check in its PR. The feature owner updates the relevant task page and screenshot; the API owner regenerates/inspects OpenAPI reference; the operator owner reviews deployment/recovery changes. CI checks links, schema drift and site build; a release reviewer executes critical tutorials and records the verified commit. Review stale screenshots and external links on a schedule, and retire obsolete docs versions only when the matching app version is unsupported.

**Generated vs authored:** generate endpoint paths, methods, schema fields, response models and validation constraints from repaired OpenAPI; review operation naming, examples, authorization and error behavior. Write concepts, prerequisites, UI steps, causal explanations, safety/cost guidance, interpretation, troubleshooting, diagrams, tutorials and release limitations by hand. An OpenAPI spec does not explain source lineage, paid calls or the difference between model-judged scores and factual accuracy.

## 9. Decisions and risks

| Decision | Recommended default and trade-off |
| --- | --- |
| Site location/framework | `docs/site/` with Docusaurus/TypeScript. It fits React and versioned docs while keeping internal plans outside public content; it adds a separate Node package/build to maintain. |
| First-release coverage | Ship T1/T2 and the minimum pages needed to complete them before broad source/evaluation coverage. This favors a complete reader journey over a large set of unverified pages. |
| Search | Local search first for offline/private usability and no service dependency; measure index size and plugin maintenance. Hosted DocSearch is an option after public hosting/crawl policy is known. |
| Public URL/hosting | Plan a separate docs origin, choose final domain and host at deployment approval. This avoids backend `/docs` path collision but requires cross-origin app links and independent releases. |
| Versioning | One current docs set with verified commit/release metadata; snapshot only for a supported behavior-breaking release. This reduces duplicate upkeep but requires precise version notes. |
| API reference | Repair OpenAPI, generate contracts, hand-write auth/examples. A handwritten-only reference would drift; generated-only pages would omit application semantics. Current schema 500 is the chief blocker. |
| Sample remote source | Prefer a reviewed public HTTPS fixture on an approved stable host; until available, make T3 conditional on the reader's own permitted source. Localhost is blocked by the SSRF boundary. Hosting and provider execution may have costs. |
| Screenshots | Capture fresh synthetic screenshots from isolated app stack. This costs review time but avoids stale labels and sensitive data from QA artifacts. |
| Shared-deployment claims | Describe configurable OIDC/KMS/Vault support and required live acceptance without calling the local stack production-ready. The deployment owner must validate external infrastructure. |
| Ownership | Require docs updates in feature PRs and a release reviewer for full journeys; otherwise content will diverge as UI and schemas evolve. |
