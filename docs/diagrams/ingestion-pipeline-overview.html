Ingestion pipeline: high-level view

How a document or website turns into a searchable index in RAG Quality Studio. Red tags mark the scaling bottlenecks from the review.

Snapshot from the 2026-10-02 scaling review, before its fixes. Bottlenecks 1–5 were addressed in commit e5e9003, and stale-run recovery changed in 92f7b44. See docs/architecture.md for current behavior.

1. Who does what

The API never does heavy work. It saves a job in PostgreSQL and returns immediately. The dispatcher and workers do the rest.

1User (browser)Uploads files or picks a source, then clicks Run
→
2FastAPI backendValidates, saves the job as queued, returns a run ID
→
3DispatcherWakes every 5 s, picks up to 20 queued jobs, sends them to Redis Bottleneck 1 · 4 · 5
→
4RedisMessage queue only. If it loses a message, the dispatcher re-sends it.
→
5Celery workersDo the actual work. 2 processes, all job types share one queue. Bottleneck 4
PostgreSQL + pgvectorThe source of truth: job status, progress, chunks, embeddings, index versions Bottleneck 7: no vector index
Disk volume /data/documentsRaw uploaded and fetched files Bottleneck 6: one machine only
OpenRouterCreates the embeddings. Limited to 60 requests/min per key (shared counter in Redis). Bottleneck 3

2. Life of one ingestion run

Each stage saves its result in PostgreSQL, so a crash resumes from the last finished stage instead of starting over.

SourceUpload, website, S3, Notion, Confluence
→
Fetch & parseDownload, extract text from PDF/TXT/HTML
→
CleanNormalize text, drop duplicates
→
ChunkSplit into pieces (max 50,000 per file)
→
Embed16 chunks per task via OpenRouter Slowest stage
→
PublishIndex becomes ready only when 100% embedded
  1. ✅ Users never query a half-built index. The previous ready index stays live until the new one is complete.
  2. ✅ Duplicate or stale workers can't overwrite each other (each attempt has its own execution token).
  3. ✅ A job stuck for more than 3 minutes is requeued automatically, up to 3 times.

3. Why embedding is slow: the 5-second loop

Each worker task embeds only 16 chunks and then hands the job back. The next batch waits for the dispatcher's next 5-second pass.

① Worker embeds 16 chunksChecks the cache, calls OpenRouter, saves the vectors
② Job set back to queuedProgress saved, e.g. 320 / 20,000 chunks
④ Redis delivers it to a workerRepeat until every chunk has a vector
③ Waits for the dispatcherUp to 5 s idle time per batch Bottleneck 1

① → ② → ③ → ④ → ① …  ≈ 190 chunks/min per index · 20,000 chunks ≈ 1.7 hours

4. Bottlenecks at a glance

#ProblemWhat users noticeFix
1One 16-chunk batch per 5-second dispatcher passLarge documents take hours to indexTask queues its own next batch immediately
2Embedding cache lookup compares full text without an indexBig projects get slower and slower, then time outStore a text hash and index it
3Hitting the rate limit counts as a failureRuns fail when many users index at onceWait and retry without counting a failure
4One shared queue, oldest job first for everyoneOne heavy user blocks all othersSeparate queues, fair pick per organization
5Jobs still queued after 30 s are sent againRedis fills with duplicates during busy periodsOnly re-send jobs that are actually lost
6Files stored on a local disk volumeCan't add worker machinesMove file storage to S3
7No HNSW index on embeddingsSearch slows down past ~100k chunks per indexAdd an HNSW index
