## 2. First-release journey and trust boundaries

1. An organization project owner/admin promotes a saved answer release and configures its widget branding, exact website origins and enabled state in Studio. Studio displays a public deployment ID, a versioned loader snippet and customer-backend instructions. They create a deployment key once and store it only in their website backend's secret store.
2. The customer places the loader once in the website's shared root layout. The loader creates a small iframe-hosted launcher on every page. It carries only public configuration. The page's own authenticated visitor session remains the customer site's responsibility.
3. On open, the loader makes a same-origin `POST` to the customer-controlled token URL with the visitor's normal session cookie. That backend checks the session and its access policy, then calls Studio's **server-to-server token exchange** with the deployment key. It returns only a five-minute widget bearer token and expiry, with `Cache-Control: no-store`; it never returns the deployment key. An unauthenticated visitor sees sign-in/authorization guidance and cannot ask.
4. The loader transfers the short-lived token to the iframe with a checked `postMessage` handshake. The iframe keeps it in memory only, calls widget answer routes with `Authorization: Bearer <widget token>`, submits one text question, polls the returned run ID, and fetches the terminal result. It renders the answer and citation excerpts. Before expiry it requests a fresh token through the same customer session path; logout, page unload or close clears its memory and transcript.
5. A copied embed script or deployment ID can render a launcher, but cannot obtain a token without that website's authenticated backend and cannot submit a question. Allowed origins narrow browser exposure; they are **not** visitor authentication. A static-only customer site has no valid first-release integration unless it adds a trusted backend or serverless function that authenticates visitors and protects the deployment key.

## 3. Embed, configuration and isolation contract

Use an **iframe** hosted on a widget-controlled origin. A Shadow DOM subtree gives style scoping but still shares the customer's document, JavaScript realm, CSP quirks, and event surface; host styles/scripts and dependencies can still interfere. The iframe gives a separate document and CSP for untrusted answers/citation text, a smaller integration surface, and an independently versioned app. The loader owns only iframe creation, placement, sizing, handshake and token delivery. The iframe owns launcher and panel UI. Closed size is only the launcher hit target; opening requests a larger desktop panel or full-screen mobile viewport. The loader sends the host page's mobile/desktop viewport mode in its checked handshake and resize messages; iframe width by itself is not the page width. A frame that cannot initialize within ten seconds shows a generic visible setup error. Guard duplicate script insertion so a root layout plus client navigation still yields one launcher.

Proposed copyable snippet (values are examples; neither is a credential):

```html
<!-- In the site's shared root layout, once per page; every route then gets the launcher. -->
<script
  async
  src="https://widget.example.com/v1.0.0/loader.js"
  data-rqs-deployment-id="55555555-5555-4555-8555-555555555555"
  data-rqs-token-url="/api/rag-widget/token"
></script>
```

`data-rqs-deployment-id` is a public opaque UUID and selects exactly one deployment; it cannot authorize a request. `data-rqs-token-url` must be a same-origin HTTPS path on the customer website (loopback HTTP only in development), accept `POST`, and never redirect to another origin. The loader validates these attributes, derives its trusted widget origin from its own versioned script URL, and rejects unsupported origins/versions. It never accepts an arbitrary API endpoint, token, key or HTML branding field from script attributes. The example host is illustrative; no CDN is selected or deployed by this plan.

Studio stores exact allowed **site origins** per deployment (`scheme://host[:port]`, no path, wildcard, userinfo or suffix matching), enabled state, limited public branding (`title`, approved color tokens, launcher position left/right, greeting and safe logo asset URL if supported), and a configuration revision. Owners/admins edit with `If-Match`; reads return no secrets. Require at least one HTTPS origin before enabling outside loopback. The loader snippet itself does not set or override the allowlist. Separate the customer page origin, widget asset/frame origin, and API origin in configuration; treat each as a distinct CSP/CORS boundary. Brand text and logo URLs are untrusted inputs and must be length/host constrained and safely rendered. The site owner adds script and frame origins to its CSP, and `connect-src` for its **same-origin token URL**; the iframe CSP permits only the selected API origin and assets. No `unsafe-inline` requirement for the loader. On exchange, the customer backend sends its server-configured canonical site origin only after validating the incoming browser Origin and authenticated session; it must not forward a visitor-supplied origin string as authority.

Pin an explicit major/minor/patch asset path (`/v1.0.0/...`) and serve immutable content with a long cache lifetime. Studio may recommend an approved version and optionally supply an SRI hash plus `crossorigin="anonymous"` for the loader. Make the frame app version match the loader's compatible protocol version. Roll out a new path instead of mutating pinned assets; retain supported old versions for a defined deprecation window. The host page can upgrade deliberately. Serve the loader as a small cacheable public file with no environment secrets; HTML/frame configuration responses containing deployment settings have a bounded cache policy and no sensitive data.

The customer backend's example contract is **its own API**, not a Studio route: `POST /api/rag-widget/token` with the customer's first-party session and CSRF/Fetch Metadata protection, returning `{token,expires_at}` or a safe `401/403/503` and `Cache-Control: no-store`. It must verify a real visitor identity or entitlement on **every issuance**, maintain a stable opaque per-login-session visitor binding (for example an HMAC of its internal session ID), call the Studio exchange from the server over TLS, and strip token/key from all logs and traces. Never embed the key, a minted token, or a CSRF secret in HTML, script attributes, URLs, local/session storage, service-worker caches or analytics. A short-lived token exists only in volatile loader/iframe memory while needed.

## 4. Additive backend contract

The existing `/v1/answer-deployments/{id}` routes remain server-to-server and continue rejecting browser `Origin`. Add **separate** routes and an auth principal for widget traffic. Version the new schema in OpenAPI with tests before implementing UI. Retain the existing answer job/worker, pinned release, admission budgets, status/result shape and safe error envelope. Do not relax global CORS or remove the existing Origin guard without route-specific policy tests.

| Route | Caller and required behavior |
| --- | --- |
| `GET /v1/answer-deployments/{deployment_id}/widget/config` | Public **non-authorizing** read for the iframe: return only enabled flag, approved public branding, protocol version and exact allowed parent origins, with bounded caching and no project/source/model/key data. This supports parent-origin validation before accepting `init`. A copied ID may read it but still cannot obtain a question token. If exposing the origin list is rejected at privacy review, substitute a deployment-aware frame bootstrap with equivalent server-validated parent-origin data; do not use unverified `postMessage` contents as the allowlist. |
| `POST /v1/answer-deployments/{deployment_id}/widget-tokens` | Customer backend only, `Authorization: Bearer rqs_live_...`, no browser Origin. Strict JSON `{visitor_session_id, site_origin}`: `visitor_session_id` is a 32–128 character opaque pseudonymous value, never an email/raw user ID; `site_origin` is the exact configured customer origin. Validate deployment/key/org/project relation, key validity, widget enabled, active deployment and allowlist. Return `201 {token,expires_at,token_type:"Bearer"}` with a five-minute TTL and `no-store`. No refresh token. The deployment key proves the customer backend's authority to assert that it authenticated this visitor; Studio does not pretend to verify the customer's session. |
| `GET /v1/answer-deployments/{deployment_id}/widget/status` | Widget bearer only. Return the same safe availability fields as server-to-server status, including `accepting_questions`; no project/pipeline details. Token expiry/revocation and the **widget frame origin** checked. |
| `POST /v1/answer-deployments/{deployment_id}/widget/questions` | Widget bearer + checked widget-frame browser Origin, `Idempotency-Key`, strict `{question}` with the existing 1–8000 character bound/body cap. Reuse admission and return the implemented accepted shape `{id,status,release_number,created_at,status_url,result_url}` with URLs under `/widget/questions/...`. A replay returns the same run without a second charge. No caller-chosen release/index/model. |
| `GET /v1/answer-deployments/{deployment_id}/widget/questions/{run_id}/status` and `/result` | Widget bearer + checked widget-frame Origin and exact visitor-session binding. Return the existing status/result serializer shape, including `retry_after_seconds` and `202` for nonterminal result. Return 404 for another visitor's run; 410 after retention or archive. Pausing stops new questions but permits the same visitor to finish reading existing runs; archive follows existing denial policy. |

On exchange, store only a keyed hash of a 256-bit opaque token, token ID, key ID/family, deployment/org/project IDs, allowed origin, hashed visitor-session binding, expiry, revocation and creation times. Use a dedicated token hash key/reference distinct from the deployment-key pepper. Store the visitor binding as a keyed hash, not the raw value. The browser token is scoped to `status`, `submit`, `poll` and `result` **for that deployment and visitor only**, never management or another deployment. Each request checks expiry, token revocation, underlying key revocation/expiry, widget enabled, deployment state appropriate to the action, and exact Origin. Logout can call a customer-backend revoke action; explicit owner pause/revoke must invalidate admission immediately. Key rotation may require a new token if the old key is revoked; the customer backend uses its replacement key. Include a bounded token/session cleanup job and a separate owner/operator revocation path. No token is placed in a URL or cookie.

Extend run ownership with an explicit `caller_kind` (`server_key` or `widget`) and widget visitor binding, plus a DB-enforced or transactionally checked deployment/org/project association. Existing server-key `client_id` family behavior stays intact. Widget idempotency uniqueness includes deployment + visitor binding + idempotency key; token refresh for the **same** customer login session can poll and replay that visitor's runs, while another visitor or a new login session cannot. Reuse deployment/org rate, queue and spend reservations; add visitor/session and token-exchange rates so one visitor cannot consume the shared key's entire allowance. Require the customer backend to rate-limit its issuance endpoint too. Keep the key family budget ceiling in place. Duplicate submissions after a network timeout reuse the same idempotency key; a deliberate new question uses a new key. A failed paid run is not retried automatically.

Use route-scoped CORS for the **dedicated widget iframe origin**, because `fetch` runs inside that iframe: allow only that exact origin, `Authorization`, `Content-Type` and `Idempotency-Key` headers, and `GET/POST/OPTIONS`; `Vary: Origin`, no wildcard origin, no credentials, no cross-origin redirects, and no CORS on key exchange or existing server routes. Validate the widget `Origin` on actual requests as well as preflight; reject missing/`null` origin for browser widget routes. The configured **customer site origins** are checked during token exchange, by the frame's `frame-ancestors` policy and by the iframe/loader handshake; the answer API cannot infer the parent site from the iframe's request `Origin`. CORS and Origin cannot stop non-browser replay of a stolen token; short TTL, visitor binding, revocation and abuse controls limit that risk. Do not equate a matching Origin header with authenticated visitor identity.

Use the current deployment error envelope `{error:{code,message,request_id,details}}` and `Cache-Control: no-store` for every token/status/result response. Define stable codes for `widget_disabled`, `origin_not_allowed`, `widget_token_expired`, `widget_token_revoked`, `visitor_session_required`, `deployment_not_active`, `rate_limited`, `queue_full`, `budget_exhausted`, `release_unavailable` and `result_expired`; preserve existing safe codes where already present. `401` triggers one fresh customer-session token request, then an explicit sign-in/expired-session state; never loop refresh on persistent 401/403. Preserve `Retry-After` on 429/503 and never leak token, question, answer, source text, raw provider body or IDs from another organization in an error.

## 5. Iframe messaging and browser security

The loader starts the iframe at its pinned widget origin with only the public deployment ID and protocol version in its URL. It generates a per-instance random handshake nonce in memory and sends an `init` message after frame load using the exact widget origin. The iframe accepts `init` only from `window.parent` at the configured customer origin, then echoes the nonce in `ready`/`open`/`close`/`token-needed`/`height` messages containing a strict version and deployment ID. The loader accepts messages only from `iframe.contentWindow` and the exact widget origin, with validated types and bounded payloads. The iframe accepts `token` only from that parent with the matching nonce/deployment/protocol; both sides use exact `targetOrigin`, never `*`. No answer, question, key, raw error or provider payload crosses the message channel. Clear the token when the panel closes or page unloads; the loader may retain only minimal UI state in memory. Reject messages from another frame, another origin, an old handshake or an unknown protocol version.

Set the iframe's `frame-ancestors` CSP to explicitly approved site origins; `X-Frame-Options: DENY` cannot be used for this frame. Because that header varies by deployment, serve the frame HTML through a deployment-aware edge/backend response with dynamic CSP while keeping its versioned JavaScript/CSS immutable and CDN-cacheable. Do not cache one deployment's frame policy for another. Do not sandbox with incompatible flags without testing the same-origin/API behavior; prefer a dedicated widget origin, tight CSP, and a minimal sandbox permission set proven by browser tests. The customer page must allow the pinned widget frame in `frame-src` and loader in `script-src`. The iframe sets restrictive `default-src`, `script-src`, `style-src`, `img-src`, `connect-src`, `base-uri` and `form-action`; no arbitrary navigation or popups in v1. Validate logo URL hosts and citation destinations if links are ever offered. Render answers, greetings, titles and excerpts as text or through a strict allowlisted markdown renderer; no raw HTML, script, `javascript:` URLs or injected styles. Citations open an in-widget inspector, not an unvalidated external URL.

Questions and answers may contain private customer content. Display a brief privacy notice linking to the customer's policy; do not capture page contents, DOM, URL, cookies, visitor email or analytics IDs. The API already retains deployed answer content for 30 days by default; Studio must show this policy and allow an operator-approved shorter retention choice before shared deployment if needed. Do not record question/answer/token in access logs, browser console, analytics, error reporting or metrics labels. `Referrer-Policy: no-referrer` on widget responses; `no-store` on token and answer requests. Browser transcript is in memory only and disappears on reload/close/logout. Evidence excerpts are limited to the current response's validated citation allowlist.

## 6. Widget UI and Studio management

**Widget:** The collapsed launcher has an accessible name that names the assistant. Enter/Space opens it; Escape closes it and returns focus to the launcher. On open, focus the heading or question field predictably; the iframe has a descriptive `title`, visible focus rings, logical tab order and an `aria-live` region for status/answer without announcing every polling tick. Do not trap keyboard focus in a nonmodal desktop panel; on narrow screens the panel is a full-screen dialog with a close button, focus containment, safe-area insets and a tested return-focus path. Support reduced motion, 200% zoom, high contrast and long localized text. Persist no chat transcript in browser storage.

Show clear states: authenticating visitor, sign-in/permission required, ready, submitting, queued, retrieving/generating, slow response (after a measured threshold, explain it is still running), transient poll interruption with bounded backoff, successful answer, insufficient evidence with no fabricated citations, safe provider failure, paused/unavailable deployment, expired session, 429 with `Retry-After`, budget exhaustion, and expired result. Keep the submitted question visible during a run. Disable duplicate submit while the same idempotency key is in flight. A retry after a transport ambiguity first reuses that key; a user-initiated new question gets a new key. For insufficient evidence show the backend's explicit state and an honest message. Render citation labels, title, page, rank and bounded excerpt in a keyboard-accessible expandable inspector; score is never called confidence. Never imply a citation is a clickable source URL unless an authorized safe URL contract is added later.

**Studio:** Add a Widget section to the existing deployment detail, visible as safe metadata to project readers but editable only by owner/admin. Show active release number and `accepting_questions`, widget enabled/paused state, exact allowed origins, branding preview in the real iframe, token URL instructions, copyable versioned snippet and a customer-backend sample for common server frameworks. The preview may show appearance without a token; a live question preview requires a separate owner/admin-only server-issued test token bound to the preview session and deployment, with explicit cost warning and normal limits. Do not silently simulate a successful answer. Show setup diagnostics for no active release, no allowed origin, disabled widget, missing token URL, token endpoint 401/403, bad CSP/frame policy, invalid branding, deployment key revoked, token exchange unavailable and public-ingress gate not met. Pause controls remain the existing deployment state action; add a separate widget-enabled toggle if owners need to stop embeds without stopping server-to-server callers. Key issuance continues to show plaintext once and tells the owner to store it only in the customer backend secret store. Public deployment ID and loader URL are safe to copy; the secret is never part of copied HTML.

## 7. Build, local development and hosting

Create `widget/` with its own strict TypeScript config, package manifest/lockfile, Vite build and tests. Build two outputs from that app: a minimal dependency-free loader script and the isolated React iframe app. Share only small typed API/branding contracts with Studio if a real duplication appears; do not import Studio auth, styles or its workspace bundle. Check loader bytes and iframe bundle size in CI against agreed budgets, and test compatibility between pinned loader/frame/API protocol versions. Add cache headers and an asset manifest to deployment packaging. Keep the build free of keys and site-specific secrets.

For local development, keep the existing Docker Compose PostgreSQL/Redis/backend/worker/dispatcher and the canonical Studio Vite frontend at `127.0.0.1:5273`. The separate widget Vite server uses `127.0.0.1:5274`, the isolated authenticated customer fixture uses `127.0.0.1:5275`, and a copied-site denial fixture uses `127.0.0.1:5276`; configure the exact allowed customer origin. Do not run a second Docker/Nginx Studio frontend or use a fallback Studio port. The API is loopback-only, so these tests prove local integration, not public reachability. Use ignored local secret configuration and deterministic provider doubles for default end-to-end tests.

Later CDN deployment serves immutable loader/frame assets over HTTPS from a dedicated widget origin with versioned paths, CSP and rollback retention; the customer token URL stays on its own origin. The answer API needs a separately designed TLS public ingress that exposes only the new token/widget routes and the approved server-to-server exchange, with gateway request-size/rate protections. Do not point a CDN at the loopback Compose service or expose management routes. Production release waits for the endpoint plan's independent identity, encryption, secret-store, ingress, backup/restore, capacity and operations gates; no gate is declared complete here.

## 10. Architectural decisions and unresolved questions

Implemented decisions: separate `widget/` app; iframe isolation; public versioned loader with public deployment ID; first-party customer backend authentication; server-to-server key only in that backend; five-minute opaque, hashed, deployment/visitor/origin-scoped widget tokens; memory-only browser token; separate browser routes sharing deployed-answer execution; exact origin allowlist as defense in depth; one active deployed answer pipeline per embed. The local fixture is a test customer backend with disposable sign-in sessions, not a reusable customer authentication product. The widget preserves existing bounded citation excerpts and 30-day deployed-run redaction. The Studio preview is appearance-only; a charged live-preview token is not implemented or implied. No logo URL support is included, so branding has only safe text, color token and launcher position.

| Open question | Recommended default and reason | Decision needed before |
| --- | --- | --- |
| Visitor identity and entitlement | Customer backend authenticates every token request and sends a stable per-login-session pseudonymous HMAC, not an email. New login session gets a new binding, so old answers are inaccessible. | Token schema and customer integration guide. |
| Token TTL and session revocation | Five minutes, no refresh token; customer token URL issues another token after rechecking session. Explicit revoke on logout when feasible; key/widget disable and pause provide operator controls. | Issuance implementation and privacy review. |
| Citation disclosure | Keep the current bounded 280-character excerpts, title/page/rank only if the deployment owner confirms this source content may reach authenticated website visitors; otherwise return safe metadata/labels. No raw document download. | Live widget enablement for a deployment. |
| Transcript/retention | Browser memory only; backend's current 30-day deployed-run content redaction is the default pending customer privacy requirements. Document erasure/export policy before internet exposure. | Customer rollout. |
| Hosting/production ingress | Dedicated HTTPS widget asset origin and route-limited API gateway after all endpoint-plan gates; no chosen CDN/cloud account now. | Any publication or external traffic. |
| Live preview cost | Appearance preview is free and read-only; live preview needs owner/admin authorization, explicit cost notice and normal budget accounting. | Studio live-preview slice. |

Later options, outside the first release: public anonymous chat with a separate abuse/payment model; file uploads; voice input/output; multi-deployment routing; conversation memory; proactive page-context ingestion; the optimization agent. None should weaken the private token boundary or silently enter the initial widget.
