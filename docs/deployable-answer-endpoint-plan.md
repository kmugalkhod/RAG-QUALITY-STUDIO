Status: **plan only, 2026-09-27**. No endpoint, schema change, public ingress, or production Clerk configuration is implemented by this document. The first deliverable is a server-to-server API. A website widget and optimization agent are outside this plan.

## 2. Product and ownership contract

### Resources and states

- A **deployment** belongs to exactly one non-null Clerk organization and one project. It has a stable opaque UUID and a human name. A project may have several deployments, but a deployment binds to one answer pipeline; creating a new deployment is required to switch pipeline identity.
- A **release** is immutable: exact pipeline version UUID, exact ready index version UUID, validated execution JSON/hash, index embedding configuration/hash, release number, runtime/schema compatibility version, creator, timestamp and optional safe note. The retriever's `index_id` **must equal** the supplied index UUID. Never override it at publish time. To use a newer index, save a new answer pipeline version whose retriever names it, then create/promote a release.
- Deployment state is `paused`, `active`, or `archived`. Creation produces a paused deployment with release 1 and no active pointer. `active` requires an active release. `paused` retains the active pointer as the last selected release; admission is disabled. `archived` is terminal, denies customer access and revokes all keys. A release does not have a mutable status; it is staged, active, or historical by comparing it with the deployment pointer.
- **Promote** explicitly points to a staged or historical release in the same deployment, after revalidating graph, project, ready index, current runtime/provider compatibility, and limits. **Rollback** is the same atomic pointer change to an earlier release, recorded with reason `rollback`. No automatic promotion or rollback occurs when a pipeline, index, provider configuration, or knowledge-set pointer changes.
- **Pause** immediately stops new admissions; already accepted jobs may finish against their pinned release. **Resume** explicitly revalidates and restores `active` on the same pointer. **Archive/delete** stops new admissions, atomically revokes keys, cancels queued runs, requests cancellation of running runs, and retains release/audit history. The management `DELETE` is soft archival, not row deletion. No restore from `archived` in v1; create a new deployment and new keys. In-flight paid provider calls may finish and be charged even after cancellation.
- Promotion affects only **new** admissions after its transaction commits. Each accepted run captures `release_id`; queued and running requests keep their original release during promotion, rollback or pause. Existing result reads may complete during pause; after archive customer reads return `410 deployment_archived` while owners/admins retain management history.
- An active deployment whose pinned model/index can no longer execute stays visibly `active` in history but reports `accepting_questions:false` and denies new admissions with a safe `503 release_unavailable` until configuration is repaired or a compatible release is promoted. Never fall forward to another index or model.
- A saved pipeline version or index referenced by any release cannot be hard-deleted through future cleanup while retention requires it. Existing API has no pipeline/index delete route. Future deletion code must honor these FKs and provide an explicit, reviewed retention process. Source-artifact expiry can make raw downloads unavailable without rewriting stored answer evidence; the customer citation response must use the saved bounded excerpt.

Every management read must first verify both live Clerk organization membership and project membership. The client may hide forbidden controls but the server is authoritative. Local-owner mode may be used for loopback development tests only; issuing usable customer keys requires an explicit local-only feature switch in development and never relaxes the public exposure gate.

## 4. HTTP API v1

All JSON is strict (`extra=forbid`), UUIDs are opaque, times are UTC ISO 8601, and errors use `{ "error": { "code": "...", "message": "...", "request_id": "...", "details": [...] } }`. Never echo submitted question, token, provider body, prompt, or hidden resource identifiers in errors. Stable codes matter more than prose. Authentication failures are `401`, project/deployment concealment is `404`, insufficient role is `403`, invalid field/schema is `422`, stale ETag or state conflict is `409`/`412`, limits are `429` or `402 budget_exhausted`, dependency unavailability is `503` with `Retry-After` when meaningful. Use `Retry-After` on `429`/transient `503` and `Cache-Control: no-store` on all key/result responses.

## 5. Key security, limits and future widget boundary

Generate at least 256 bits of randomness per key. Parse a non-secret public ID for indexed lookup, compute a versioned HMAC-SHA-256 of the entire token with a dedicated server pepper from a secret store, and compare in constant time. Database contains only hash, prefix and metadata. Use a distinct credential type so Clerk JWTs never authenticate customer routes and deployment keys never authenticate management routes. Strip `Authorization`, `Idempotency-Key`, questions, prompts, raw evidence, and response bodies from access logs, tracing, exception handlers and metrics labels. Prevent key-bearing responses from browser caching, analytics and error reporting. No key in URL or query string.

At admission enforce, in a single PostgreSQL transaction, key validity, deployment active state, pinned release validity, idempotency, per-key/deployment/org rate budgets, global queue cap, and a monetary reservation. Redis may accelerate rate checks but PostgreSQL remains authoritative across restart/failover. Recommended initial **operator-configurable ceilings**: 10 accepted questions/minute/key, 30/minute/deployment, 100/minute/organization; 2 concurrent running/deployment, 10/org, 20 queued/deployment and 100 queued/org; 8,000 question characters and one question per request. Concurrency slots are claimed/released transactionally with lease expiry/fencing. Refuse admission with `429 rate_limited`, `429 queue_full`, or `429 concurrency_limited` and `Retry-After`.

For spending, publishing requires an approved pricing basis for both query embeddings and generation model, a per-run **worst-case upper bound** from bounded input/context/output tokens, plus per-deployment and per-organization daily/monthly limits. Recommended development defaults: $5/day and $20/month per organization, with a global operator ceiling and `max_reserved_usd_per_run` of $0.25. Reserve worst-case cost at admission; the sum of settled plus outstanding reservations cannot exceed the limit. Settle provider-reported cost when complete; if cost or completion is ambiguous, retain the full reservation as conservatively spent until reconciled from provider billing. Never treat unknown cost as zero. No automatic retry after an ambiguous paid call. If a configured model lacks a safe price ceiling or provider billing changes unexpectedly, fail closed with `503 pricing_unavailable` and pause new admissions operationally. This is an application admission budget, not a guarantee of exact third-party billing; separately configure provider/account spend caps and alerts.

Future private widget: a website must **not** contain this server-to-server key. A separate backend token-exchange service would authenticate an end user or signed customer session, bind an allowed origin/domain and deployment, mint a short-lived narrow submit/poll token, apply user/session limits and abuse controls, and authorize only that user's results. CORS and domain checks alone do not authenticate callers. No widget route, token minting, browser key storage or public anonymous access is in scope now.

## 6. Durable execution and failure semantics

1. `POST /questions` locks deployment/limit rows, validates active release and model/index compatibility, stores a queued run and budget reservation, commits, and returns promptly. It does not call OpenRouter. The dispatcher scans durable queued rows with `FOR UPDATE SKIP LOCKED`, sends only run IDs to Redis/Celery and records `dispatched_at`. Redis outage leaves the database queue intact; duplicate delivery is expected.
2. A dedicated deployed-answer Celery task claims `queued → running` with a fresh execution token, attempt count, deadline and heartbeat. Only the current token may checkpoint or finish; stale deliveries exit. Use the saved release's execution and exact index UUID, not `pipelines.name`, a latest version, or `knowledge_sets.current_ready_index_id`. Reuse `compile_answer_chain`/provider adapters through an application-owned executor and a fenced checkpoint callback; do not call the existing unguarded `queries.finish` directly. Existing playground and experiment contracts stay intact.
3. Persist retrieval evidence (bounded text and provenance), ranks, score semantics, prompt/model/runtime versions, exact index/release IDs, answer, validated citations, insufficient-evidence state, usage/cost basis and timings. Customer result serializer exposes only its allowlisted subset. Check cancellation and execution token before paid embed/generation calls, between stages and before final write. Query latency excludes queue wait; measure both separately.
4. Provider HTTP connect/read/total timeouts must fit below the Celery soft/hard limit with margin for DB checkpoints. The current chat adapter has 5-second connect/45-second HTTP timeout and 55-second response deadline; embedding adapter limits must be reviewed as part of the worker slice. Give deployed tasks a dedicated queue or reserved capacity so ingestion/experiments cannot starve them, and bound per-org active claims. Avoid stacked provider/Celery retries.
5. Retry automatically only before any paid provider request, for bounded transient infrastructure failures (default max 2 attempts, exponential backoff with jitter). Record a durable `provider_call_started` marker **before** each paid request. Once a paid call may have started, a crash, timeout or lost response is ambiguous: mark the run failed with safe `provider_outcome_unknown`, retain its reservation and require a new client request with a new idempotency key. A provider's explicit no-charge transient rejection may be retried only if its contract proves no work occurred. Never repeat generation merely because Celery redelivered.
6. Dispatcher recovers stale `running` rows by heartbeat/deadline, clears their token and either requeues safe pre-provider attempts or fails ambiguous paid attempts. It also re-dispatches queued rows after a bounded visibility interval. `cancel_requested` prevents new calls; queued jobs become `cancelled` immediately and release reservation; running jobs reach `cancelled` after a safe checkpoint or are fenced by deadline. Terminal writes are compare-and-set, so a stale worker cannot overwrite cancellation or a newer attempt.
7. Pause affects admission only. Archive cancels queued and requests cancellation of running jobs. Operator shutdown drains or fences jobs before replacing workers. Results must survive process/Redis restart because PostgreSQL is source of truth. Worker crashes, DB commit ambiguity and provider failures have distinct safe codes and audit/metric events.

These are independent release gates; this plan does not claim any is complete. Publicly reachable customer routes must remain disabled until all gates and security/load tests pass.

## 10. Decisions needing owner input before implementation

These decisions change data exposure, spending or retention. Recommended defaults let planning proceed; they are **not** approval to expose the endpoint publicly.

1. **Spend ceilings and pricing authority:** Recommend a $5/day and $20/month organization admission budget for development, $0.25 worst-case per request, and a server-maintained approved upper-bound price table. Confirm the intended paid-provider account, budget owner and production limits before enabling any key. If exact provider cost remains unknown, hold the full reservation and reconcile from billing.
2. **Customer-visible evidence:** Recommend answer plus short citation excerpts, title/page and rank, with no raw chunk download or full prompt/messages. Confirm whether citations may contain confidential document text; if they may not, use citation IDs and safe metadata only.
3. **Retention:** Recommend 30 days of question/answer/citation results and at least 365 days of release/key/audit/usage history, subject to legal/privacy requirements. Confirm a shorter or longer policy before cleanup is implemented.
4. **Production exposure target:** Recommend a private, TLS-authenticated ingress to the server-to-server route after the separate Clerk, encryption, ingress and AWS gates; no public anonymous traffic. Confirm the intended AWS account/region, operational owner, and whether keys should be scoped to a customer tenant beyond one deployment before infrastructure work.

Until those choices and gates are settled, build and verify against local/isolated services only. The present system is **not production-ready** for deployable answer traffic.
